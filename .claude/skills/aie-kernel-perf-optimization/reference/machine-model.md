# AIE2P machine model for bound calculations

Use this to compute a loop's resource bound (ResMII) and recurrence bound
(RecMII) *before* editing code. Ground truth is the compiler's model in
`llvm/lib/Target/AIE/aie2p/` of the llvm-aie (Peano) source.

## Contents
- Issue slots
- Shared ports
- Register budget
- Looking up latencies
- Load-slot binding (bank -> slot)
- Worked example: bounding a MAC loop

## Issue slots (one op per slot per bundle)

| slot | typical ops | note |
|---|---|---|
| load A (`vlda`, `lda`) | vector/scalar loads, `vlda.pop/fill` (FIFO), `vlda.conv` | `vlda.conv` (load + bf16->fp32) exists only here |
| load B (`vldb`) | vector loads, `vldb.pop/fill`, `vldb.*.unpack`, and register `vunpack` | `vunpack` (int4 -> int8 in registers) competes with slot-B loads |
| store (`vst`, `st`) | `vst`, `vst.conv` (SRS store), `vst.push/flush` (output FIFO), SRS into a register (`vconv.bf16.fp32`, `vconv.bfp16ebs8.fp32`) | ONE store per cycle: 1024-bit accumulators need 2 stores (cml/cmh); a bfp16 block push is a `vst.push.576.conv` plus a `vst.flush.512.conv`, and consecutive pushes chain (RecMII ~3 per panel) |
| vector (`vmac`, `vmul`, `vadd`, ...) | MAC/MUL/elementwise, accumulator add/sub (`vadd.f`, `vsub.f`) | one MMUL-class op per cycle |
| mv (move) | `vconv.fp32.bf16` (x -> cm), `vextract`, `vextbcst`, `vband`/`vbor`, `vsel`, compares and min/max (`vlt`, `vmax_lt`, `vmin_ge`, `vabs_gtz`), the LUTs `vtanh`/`vexp2` (16 lanes each), `mov eh/el`, register copies | single slot; often the hidden bottleneck of shuffle/dequant loops and of LUT activations (32-lane SiLU: 2 `vtanh` + 2 `vexp2` + compare + select + UPS) |
| scalar ALU (`add`, `lshl`, `mul`) | pointer and counter math | scalar `mov` and `vups` are mv-slot ops, `movs` (pointer copies) a store-slot op, `padda` / `paddb` / `padds` go on the load A / load B / store slot (llvm-aie's TableGen; `artlite.variant_search` counts by it) |

Count ops per iteration per slot from the loop body in the `.s` file
(everything between the loop label and `.L_LEnd`), e.g.:

```bash
for op in "vlda.pop" "vldb.pop" "vlda.fill" "vldb.fill" "vlda.conv" "vst" "vmac" "vconv"; do
  echo "$op: $(grep -c "$op" body.s)"; done
```

ResMII = max over slots of (ops on that slot), and over the shared ports
below. If the achieved II is well above that, the limit is a recurrence or
register pressure, not resources.

## Shared ports

Besides its slot, an op occupies the itinerary's units (llvm-aie
`aie2p/AIE2PGenSchedule.td`); a few register-file and memory ports are used by
ops of several slots, so a loop can be port-bound while every slot has room.
The post-pipeliner's ResMII counts slots only: it then fails "out of
resources" at every II up to the port count. `artlite.variant_search` (`port`
column, `res bound`) and the `ARTLITE_MEASURE_II` report (`res bound` line)
count them per loop body (tables: `artlite/aie2p_isa.py`, generated by
`python -m artlite.gen_isa_tables`):

| port | ops (per instruction: 1) |
|---|---|
| `rm` L_RM_PORT | `vshuffle`, `vsel`, `vbcst`, `vinsert`, `vshift`, `vpush.*`, `vaddsub`, `add.nc`, `mov.d*`, and every `vst.push.*` / `vst.flush.*` (a bfp16 panel push is 2) |
| `wm` L_WM_PORT | `vextract`, compares (`vlt`, `vge`, `veqz`), `vmax_lt` / `vmin_ge`, `vabs_gtz`, `movxm`, the pushes / flushes |
| `qwa` QEY_WA_L0_PORT | SRS (`vconv.bf16.fp32`, `vsrs`, `vconv.bfp16ebs8.fp32`), `vfloor`, `vpack`, and slot A's `vlda.pop.*`, `vlda.128`, `lda` |
| `qwb` QEY_WB_L0_PORT | slot B's loads and pops, `vunpack`, the gathers `vldb.4x*` |
| `qrs` QEY_RS_L0_PORT | scalar stores, `vst.128`, `vst.pack`, plain `vst.push`, `vunpack`, the gathers |
| `dwm` DM_WM_L0_PORT | `vconv.fp32.bf16`, `vups`, `vlda.conv` / `vlda.ups` |
| `ada` DM_ADA | slot A's memory accesses and the gathers |

Example: GemmQ's dequant pushing 8 panels per iteration (16 `rm`) with 30
shuffles runs at II 46 = 30 + 16 while mv counts 30; broadcast + transpose
expansions (`vextbcst.128` is not on the port): 40 (restructurings.md R7).

## Register budget (compiler view, `AIE2PRegisterInfo.td`)

| class | count | aliasing |
|---|---|---|
| `dm` (2048-bit accumulator, 64 x fp32) | 5 | = 10 `cm` (1024) = 20 `bm` (512) |
| `ex` (576-bit block-float: 512 mantissa + 64 exponent) | 12 | overlap the `x` registers |
| `x` (512-bit) | 12 | = 24 `wl/wh` (256) = 6 `y` (1024) |
| `p` pointers | 8 | includes `sp`; every live stream/pointer needs one |
| `m` modifiers | 8 | |
| `d` (2D iterator state) / `d*_3d` | 8 / 4 | each `add_2d_*` / `add_3d_*` iterator (and 2D/3D FIFO pops) holds one |
| `r` scalar | 32 | |
| `lf` load-FIFO state (1024-bit) | 2 | at most two input streams (`fifo_ld_*`, block_vector input streams) live at once |

Four 8x8 fp32 accumulators + one staging accumulator is the practical
maximum for MMUL loops; a design needing a fifth live accumulator spills.
What counts against the 5 `dm`:
- every live `aie::accum` (also 32-lane ones: a bf16 `vmac.f` writes a whole
  `dm`, so four 32-lane accumulators already take 4);
- an MMUL result on its way to a conversion (the transient);
- `aie::accum` constants, e.g. a polynomial coefficient used as a MAC's
  initial value.
Pass constants as `vector` operands where the formula allows. 2 outputs
(y0, y1) + 2 MMUL chains (c0, c1) fit; 4 outputs + the transient spill
(restructurings.md R1).

## Looking up latencies

```bash
cd llvm-aie/llvm/lib/Target/AIE/aie2p    # in an llvm-aie checkout
grep -n "def VMAC_F\b\|\"vmac.f\"" AIE2PGenInstrInfo.td      # find the itinerary class
grep -n "InstrItinData<II_VMAC_f_vmac_bf_vmul_bf_core_X_X" AIE2PGenSchedule.td
```

The operand list gives the cycle each operand is written/read, e.g.
`[/*dst*/6, /*acc1*/4, ...]`: result written at 6, accumulator input read
at 4; a dependence's latency is def - use + 1 (LLVM's itineraries), so dependent MACs on one accumulator issue every
3 cycles.
Values read this way:

| op | latency |
|---|---|
| `vmac.f` (bfp16/bf16 MMUL) | dst @6, acc-in @4 -> chained every 3 cycles: the post-pipeliner's RecMII 3 per MMUL of an accumulator chain in an iteration |
| `vlda.conv.fp32.bf16` | dst @7 |
| `vconv.fp32.bf16` (mv slot) | dst @2 |
| `vmul.f` (bf16 x bf16) | dst @6, sources read @1 -> a dependent SRS / mul 5 cycles later |
| `vconv.bf16.fp32` (SRS, store slot) | dst @2, source read @1 |
| `vtanh` / `vexp2` (mv slot, 16 fp32 lanes -> 16 bf16) | dst @2, source read @1 |
| `vlda.pop.576` / `vldb.pop.576` | dst @8; FIFO state @7 -> one pop per cycle per stream, plus its `vlda.fill.512`s on the same slot: a 576-bit pop takes 1.125 fills of 512 bits, and the schedule carries one per pop at any unroll (the qwen35 decode's qk<2> unrolled 2 / 4 / 8: 16 fills for 16 pops per iteration): a panel per 2 cycles on its slot |

Consequences:
- One MMUL accumulator chain issues at most every 3 cycles: three independent
  chains fill the vector slot, and k MMULs per iteration on one chain bound the
  II at 3 k (the qwen35 decode's qk: a set's K hi and K lo products on one chain,
  II 6; a chain per set and K half, II 4 = its pops).
- An fp32-emulated multiply (bf16 split, 3 MACs, 2 conversions) is ~20
  cycles of latency. A chain of them bounds the II by its length, however
  empty the slots are.

## Load-slot binding (`AIEMultiSlotInstrMaterializer.cpp`)

Loads that can issue on either slot are "multi-slot pseudos". Before the
post-RA pipeliner runs, the materializer binds them per basic block:

1. Loads that are already slot-specific (e.g. `vlda.conv`, slot A) claim
   their DM bank's slot first.
2. Each remaining load's bank (from its `__aie_dm_resource_*` annotation)
   gets the slot already bound to that bank, else a free slot, else a
   round-robin slot. Order = program order of the first load of each bank.
3. A bank maps to ONE slot, so a whole stream lands on one slot.

Loads into accumulator registers (`vlda` into `bm` / `cm`, `vlda.conv`) issue on slot A only, whatever their bank
annotation: an fp32 C tile's loads all sit on slot A. A bf16 value added to an accumulator (`aie::add(acc, load)`)
fuses into a `vlda.conv`; as a MAC operand with ones (`aie::mac(acc, load, ones)`, the same exact sum) it is a plain
load that slot B can take (the vision overlay's `sd15_res_f2b`: slot A 3 -> 2 ops, II 4 -> 2).

Consequences:
- A loop with three banks puts two of them on the same slot. Put the
  heaviest stream alone on a slot, e.g. by making its first load come
  first in program order or by sharing an annotation with a light stream.
- A load without a bank annotation gets a bank-blind choice (warning
  "No memory bank assigned to load ...").

## Worked example: bounding a MAC loop (`gemm/mac.py`, 16x16 C block, k=64)

Per iteration: 32 `vmac` (vector slot), 32 FIFO pops + 4 fills, 8 C loads
(`vlda.conv`, slot A only), 8 `vst.conv` (4 accumulators x 2 halves).
Loads: 26 on the slot with the C loads, 18 on the other -> **ResMII = 32**
(vector slot).

Register view: in kstep-major order each accumulator's 8 MACs span ~28
cycles plus init and SRS store, and the 4 chains hand over (store old C,
load new C) at nearly the same time; with 5 `dm` that only works if the
post-RA pipeliner can re-allocate the accumulators (VReg mode), which it
does once nothing else pins the loop. The same order runs at II = 42 (~10
bundles per iteration without a `vmac`) when any of these holds, none of
them the accumulators themselves:

- the next block's C pair prefetched into `x` registers (loop-carried, so
  not re-allocatable, and the operand pops need those `ex` registers);
- one C-block pointer serving the early C loads and the late C stores, a
  ~50-cycle lifetime the next iteration has to wait for;
- iteration i's C stores and iteration i+1's C loads not provably
  independent.

With C loaded by `vlda.conv` inside the iteration, separate walking load
and store pointers, and the two pointers passed as distinct `__restrict`
parameters of an inlined helper, it schedules at II = 32 = ResMII. Lesson:
when II sits above ResMII without spills, look for loop-carried registers,
long-lived pointers and unproven memory independence before blaming the
register file.
